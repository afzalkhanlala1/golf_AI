# BUILD SPEC — Golf AI Swing Analysis Web App

You are building a production web application. Read this entire document before writing code. Work through the phases in order and stop at each checkpoint for review.

---

## 0. What we are building

A web app where a golfer uploads a slow-motion video of their golf swing and receives:

1. A **Swing Score** (0–100) broken into six per-phase sub-scores.
2. **Detected faults** from the TPI "Big 12" taxonomy, with severity.
3. **Coaching feedback** in plain language, plus drills — generated by an LLM that is grounded in measured numbers and structurally incapable of inventing them.
4. **Progress tracking** across sessions.

The golfer films with their phone's native slow-motion camera and uploads the file. **We do not record video in the browser** — see §2.4 for why this is non-negotiable.

### Reference material the user will supply

- `https://github.com/wmcnally/golfdb` — GolfDB: 1,400 annotated golf swings, 8 labelled swing events, plus the SwingNet baseline model (MobileNetV2 + bidirectional LSTM). Read the repo to understand the event taxonomy and the model interface.
- `https://www.kaggle.com/datasets/marcmarais/videos-160` — the GolfDB videos at 160×160 resolution.

**Use these for reference and for the optional evaluation harness only.** Model training is explicitly out of scope (§10). Do not download the dataset into the repo; add `data/` to `.gitignore`.

## 1. Hard constraints — read these first

These are the constraints that determine the architecture. Violating any of them produces an app that cannot deploy.

| Constraint | Consequence for your design |
|---|---|
| **Vercel has no GPU** | All ML inference runs in a separate service. Vercel only orchestrates. |
| **Vercel serverless request body limit is 4.5 MB** | Video must be uploaded **client-side directly to blob storage**. It must never pass through a Next.js API route. |
| **Vercel function max duration is 60s (Hobby) / 300s (Pro)** | Analysis must be **asynchronous**. Submit → poll/stream → render. Never block a request on inference. |
| **Browsers cannot capture high-framerate video** | iOS Safari caps `getUserMedia` at ~30fps and exposes no API to the phone's 120/240fps slow-motion mode. Android needs the native Camera2 high-speed API. At 30fps a 100mph clubhead moves several feet between frames. **v1 is upload-only.** Do not build an in-browser recorder. |
| **30fps is the accepted floor, 120fps is the target** | Clips below 24fps are rejected outright (unusable). Clips from 24–120fps are analyzed but flagged `low_fps`, with confidence damped sharply on impact/downswing metrics and the `fpsAdequate` flag set false — never silently presented as full-confidence. |
| **A single camera cannot measure certain things** | See §7.3. Never emit wrist flexion, ground reaction force, weight distribution, clubhead speed, ball speed, spin, or carry distance. |

Native capture is a later phase and is out of scope here.

## 3. The contract between web and inference

This is the most important file in the project. Define it **first**, in `contract/analysis.schema.ts`, as Zod schemas. Generate `analysis.schema.json` from it via `zod-to-json-schema` in a `pnpm contract:build` script. The Python service validates its output against that JSON Schema before returning.

```ts
export const SwingEvent = z.enum([
  "address","toe_up","mid_backswing","top",
  "mid_downswing","impact","mid_follow_through","finish",
]);

export const AnalysisResult = z.object({
  schemaVersion: z.literal("1.0"),
  swingId: z.string().uuid(),
  status: z.enum(["OK","REJECTED"]),
  rejectionReason: z.string().nullable(),

  capture: z.object({
    fps: z.number(),                 // TRUE fps from ffprobe, not container metadata
    width: z.number(), height: z.number(),
    frameCount: z.number(),
    durationMs: z.number(),
    view: z.enum(["face_on","down_the_line","unknown"]),
  }),

  quality: z.object({
    poseConfidenceMean: z.number().min(0).max(1),
    fpsAdequate: z.boolean(),        // fps >= 120
    fullBodyInFrame: z.boolean(),
    warnings: z.array(z.enum([
      "low_fps","low_light","partial_body","multiple_people",
      "camera_moved","view_ambiguous","short_clip","no_swing_detected",
    ])),
  }),

  events: z.array(z.object({
    event: SwingEvent,
    frame: z.number().int(),
    timestampMs: z.number(),
    confidence: z.number().min(0).max(1),
  })),

  metrics: z.array(z.object({
    key: z.string(),                 // see §7.1
    value: z.number(),
    unit: z.enum(["deg","ratio","norm","ms","index"]),
    phase: z.enum(["setup","backswing","top","downswing","impact","finish","full"]),
    confidence: z.number().min(0).max(1),
    target: z.object({ min: z.number(), max: z.number() }).nullable(),
  })),

  faults: z.array(z.object({
    code: z.enum([                   // TPI Big 12
      "s_posture","c_posture","loss_of_posture","flat_shoulder_plane",
      "early_extension","over_the_top","sway","slide",
      "reverse_spine_angle","hanging_back","casting","chicken_wing",
    ]),
    severity: z.number().min(0).max(1),
    phase: z.string(),
    detectedFrom: z.array(z.string()),   // metric keys that triggered it
    confidence: z.number().min(0).max(1),
  })),

  keypointsUrl: z.string().url().nullable(),  // blob JSON, NOT inline
});
```

**Keypoints are never returned inline.** A 5-second 240fps clip is ~1,200 frames × 17 keypoints × 3 floats. The inference service writes them to blob storage as gzipped JSON and returns the URL. Postgres stores the URL only.

## 6. Scoring — `src/lib/scoring/`

### 6.1 Design rules

- **Everything is a pure function.** Input: `AnalysisResult`. Output: scores + explanations. No I/O, fully unit-testable.
- **Every deduction must be attributable.** The UI shows *which metric* cost the golfer points. A score without attribution is worthless for coaching.
- **Confidence-weighted.** A metric with confidence 0.4 contributes proportionally less and the UI marks it as low-confidence.
- **All weights and target bands live in one file**, `rubric.config.ts`, versioned with a `RUBRIC_VERSION` constant stored on each score row. These will later be recalibrated against coach rankings — make that a config change, not a code change.

### 6.2 Metric scoring function

```ts
function scoreMetric(value: number, target: {min:number;max:number}, tolerance: number): number {
  if (value >= target.min && value <= target.max) return 100;
  const d = value < target.min ? target.min - value : value - target.max;
  return Math.max(0, 100 - 100 * (d / tolerance));
}
```

Phase score = confidence-weighted mean of that phase's metric scores.
Overall = weighted mean of phase scores, weights in config.

**Do not benchmark amateurs against raw Tour ranges.** Target bands are set for a mid-handicap golfer; store Tour ranges separately and show them as an aspirational marker in the UI, not as the scoring target.

### 6.3 Fault detection

Faults are derived from metrics via explicit, readable rules in `faults.ts` — one function per fault, each returning `{severity, detectedFrom, confidence}` or null. Example:

```ts
// early_extension: hips move toward the ball, away from the address "tush line"
export function detectEarlyExtension(m: MetricMap): FaultHit | null {
  const d = m.hip_depth_change_downswing;         // normalized by hip width
  if (!d || d.value < 0.06) return null;
  return {
    severity: clamp01((d.value - 0.06) / 0.20),
    phase: "downswing",
    detectedFrom: ["hip_depth_change_downswing", "spine_angle_change"],
    confidence: d.confidence,
  };
}
```

Only surface faults with `severity > 0.25` and `confidence > 0.5`. **Rank them and show at most the top three**, with only the top one designated the primary focus.

## 7. Inference service — `inference/`

### 7.1 Pipeline

1. **Decode** — `ffprobe` for true fps (container metadata lies). Reject clips under 1s or over 20s. Downsample to max 1080p long edge. Reject clips under 24fps outright; clips from 24–120fps are accepted with a `low_fps` warning and damped confidence (see §7.2). Correct phone display-matrix rotation (`pipeline/orientation.py`) before any downstream processing sees a frame — portrait clips are frequently stored sideways in the encoded stream.
2. **Pose** — RTMPose (via `rtmlib`, ONNX runtime, Apache-2.0) top-down with an RTMDet person detector. Track the largest persistent person; flag `multiple_people` if others are present. Emit 17 COCO keypoints + confidence per frame. Before event detection, reject clips with no real swing motion (`events.has_swing_motion` — wrist vertical travel under 10% of frame height) rather than emitting event frames off wrist noise.
3. **Events** — two strategies, in order:
   - If `SWINGNET_CHECKPOINT_URL` is set, load the SwingNet checkpoint and run it. Preprocess exactly as GolfDB's repo does (160×160, its normalization).
   - **Otherwise fall back to a heuristic detector** from wrist-keypoint kinematics: `address` = first sustained low-motion window; `top` = wrist trajectory apex / velocity sign reversal; `impact` = peak wrist speed near the lowest hand position; `finish` = last sustained low-motion window; interpolate the intermediate four. Emit lower confidence values for heuristic events.

   **Build the heuristic path first** so the service is functional without any checkpoint.
4. **View classification** — face-on vs down-the-line from shoulder-line width relative to hip width and torso depth. Emit `unknown` and a `view_ambiguous` warning when uncertain.
5. **Metrics** — §7.2.
6. **Faults + scoring** — do these in **TypeScript**, not Python. The service returns metrics only; scoring lives in the web app so it is versionable and testable in one place.
7. **Write keypoints** to blob, return the URL.
8. **Callback** to `/api/swings/:id/callback` with an HMAC-SHA256 signature over the raw body using `INFERENCE_SHARED_SECRET`. The route must verify it and reject on mismatch.

### 7.2 Metrics to compute

All values must be **scale-invariant**: use angles, or normalize distances by shoulder width or hip width. Monocular video has no absolute scale.

| key | unit | phase | definition |
|---|---|---|---|
| `tempo_ratio` | ratio | full | frames(address→top) / frames(top→impact). Target 2.7–3.3 |
| `backswing_duration_ms` | ms | backswing | |
| `shoulder_turn_top` | deg | top | shoulder-line rotation vs address |
| `hip_turn_top` | deg | top | hip-line rotation vs address |
| `x_factor_top` | deg | top | `shoulder_turn_top − hip_turn_top` |
| `spine_angle_address` | deg | setup | mid-hip→mid-shoulder vector vs vertical |
| `spine_angle_change` | deg | impact | \|spine angle at impact − at address\| |
| `spine_tilt_top` | deg | top | lateral tilt; negative = reverse spine |
| `hip_depth_change_downswing` | norm | downswing | hip-centre movement toward camera/ball vs address, ÷ hip width → early extension |
| `hip_lateral_backswing` | norm | backswing | lateral hip drift ÷ hip width → sway |
| `hip_lateral_downswing` | norm | downswing | → slide |
| `head_movement` | norm | full | max head displacement ÷ shoulder width |
| `lead_arm_angle_top` | deg | top | shoulder–elbow–wrist |
| `lead_arm_angle_impact` | deg | impact | → chicken wing |
| `kinematic_sequence_index` | index | downswing | see below |
| `shoulder_plane_top` | deg | top | shoulder-line inclination → flat shoulder plane |
| `weight_forward_finish` | norm | finish | hip-centre lateral position at finish ÷ stance width |

`kinematic_sequence_index`: compute angular-velocity time series for pelvis, thorax and lead arm through the downswing. Find each peak's timestamp. Return `1.0` when the order is pelvis → thorax → arm with sensible gaps, decaying toward `0.0` as the ordering degrades. **Report this as directional** — it is a proxy for what K-Vest measures with sensors, and it must be labelled as such in the UI.

### 7.3 Never emit these

Hard rule. Do not compute, return, display, or let the LLM mention:

- lead wrist flexion / extension / radial deviation (needs an 800Hz sensor)
- ground reaction force, pressure, or weight distribution (needs a force plate)
- clubhead speed, ball speed, spin, launch angle, smash factor, carry distance
- any injury, medical, or physiotherapy claim

If a metric cannot be computed reliably from the detected view, **omit it** rather than emitting a low-confidence guess. Missing is honest; wrong is not.

## 8. Feedback generation — `src/lib/feedback/`

The single most important architectural rule in this project:

> **The LLM explains. It never measures.**

### 8.1 Flow

1. Deterministic rules build a `FindingsPayload`: top faults, their severities, the specific metric values with their targets, phase scores, and the golfer's trend versus their last three swings.
2. That payload — **JSON only, never video, never raw keypoints** — goes to Claude.
3. The model returns structured JSON, validated with Zod.
4. A **numeric grounding validator** runs before anything is persisted.
5. On failure, retry once with the violation named; on second failure, fall back to a deterministic template. Never show unvalidated output.

### 8.2 Output schema

```ts
const Feedback = z.object({
  headline: z.string().max(80),         // one encouraging, specific sentence
  primaryFault: z.string(),             // must equal findings.faults[0].code
  whatIsHappening: z.string().max(400),
  whyItMatters: z.string().max(300),
  drills: z.array(z.object({
    title: z.string(), cue: z.string(), reps: z.string(),
  })).min(1).max(2),
  oneThingToFocusOn: z.string().max(140),
});
```

### 8.3 The grounding validator — implement this carefully

```ts
export function validateGrounding(text: string, findings: Findings): string[] {
  const violations: string[] = [];
  const allowed = collectAllowedNumbers(findings);   // metric values, targets, scores, deltas
  for (const n of extractNumbers(text)) {
    if (!allowed.some(a => Math.abs(a - n) <= Math.max(0.5, Math.abs(a) * 0.02))) {
      violations.push(`Ungrounded number: ${n}`);
    }
  }
  for (const term of BANNED_TERMS) {               // §7.3 list + medical vocabulary
    if (text.toLowerCase().includes(term)) violations.push(`Banned term: ${term}`);
  }
  return violations;
}
```

Whitelist trivial integers (rep counts 1–20, ordinals) via the `reps` field being generated separately from a fixed vocabulary. Write unit tests that feed deliberately hallucinated text through this and assert rejection.

### 8.4 Coaching principles to encode in the system prompt

- **One focus at a time.** Name a single primary fault. Overloading a golfer with swing thoughts is how instruction fails.
- Open with something genuinely working in the swing, drawn from the highest-scoring phase.
- Reference the golfer's own numbers and their trend, never generic advice.
- Plain language. No jargon without a one-clause explanation.
- Never diagnose pain, injury, or physical limitation.
- If `quality.warnings` is non-empty, say so plainly and reduce the confidence of the advice.

## 14. Club delivery, 3D playback, fitting and Live Coach

### 14.1 The governing rule: withhold rather than approximate

Everything in this section is measured from one consumer camera. A single
camera cannot see motion along its own optical axis, and it cannot sample
faster than it records. Where those limits bite, the pipeline emits **no
number and a reason**, never a degraded one.

That distinction matters and is not a confidence question. A down-the-line
clubhead speed is not noisy — it is *biased*, by a factor of two or three,
and no confidence score repairs a bias. Same for frame rate: at 30fps a
100mph clubhead travels ~1.5m between exposures, further than the club is
long, so there is nothing to track rather than something to track poorly.

Hard gates, enforced in `inference/pipeline/club.py`:

| Output | Requires |
| --- | --- |
| Swing tracer | ≥60fps |
| Clubhead speed, attack angle | ≥60fps **and** face-on |
| Ball speed, smash factor | ≥120fps **and** face-on |
| 3D playback, ghost | nothing extra — works at 30fps |
| Club path (in-to-out) | **not emitted at all** — see below |

3D playback needs no high frame rate because world landmarks come from the
pose model on each frame independently; there is no inter-frame tracking to
break down.

**Club path is deliberately absent.** It is an angle relative to the target
line. Face-on, the target line runs along the camera axis, where there is no
signal. This is a monocular limit, not a tuning problem, and it should not be
added without a second camera.

### 14.2 Scale — `inference/pipeline/scale.py`

Pixels-to-metres from MediaPipe's metric reconstruction: body segment lengths
in pixels against **their projection into the world x/y plane**. Dropping the
world z component is what makes it correct — comparing against full 3D length
inflates the scale for any segment angled toward the camera.

### 14.3 Club tracking — `inference/pipeline/club.py`

Three-frame differencing (cancels the trailing motion ghost), torso
suppression, a club-length annulus around the hands, then a second pass
against a tight band around the radius the first pass actually observed.
Ball speed uses a small RANSAC over post-impact blobs, because the clubhead
is still moving fast beside the ball and passes every size and distance
filter — what it cannot do is stay on the ball's straight line.

**Two independent accept/reject layers**, and both are load-bearing:

1. The frame-rate and view gates above.
2. A physical check on the track: rigidity (a clubhead holds a fixed distance
   from the hands) **and** reach in metres against what is actually in a golf
   bag. Rigidity alone is insufficient — on real footage a track locked onto
   a forearm held a beautifully consistent 0.62m radius and passed. The reach
   test uses the 90th percentile so a foreshortened down-the-line club is not
   penalised for it.

### 14.4 3D playback — `src/lib/three-d/skeleton3d.ts`

Ghost comparison removes three mismatches, each measured **once at address
and applied to every frame**:

- **Size** — divide by torso length. Per-frame would pump the skeleton larger
  and smaller as the torso foreshortens through the turn.
- **Facing** — rotate the stance to a canonical bearing. Per-frame would
  square the body up on every frame and *erase the shoulder turn*, which is
  the thing a golfer opens 3D to see. A test pins >60° of turn surviving.
- **Timing** — piecewise-linear warp through shared events, so address sits
  on address and impact on impact at any tempo.

### 14.5 Live Coach — `/coach`

Real-time **setup** coaching from the webcam: spine angle, knee flex, stance
width, head position. Runs entirely client-side via `@mediapipe/tasks-vision`;
no frame leaves the browser and nothing is recorded.

It does not analyse swings, and the UI says so. A webcam is ~30fps and a
downswing is ~7 frames — live swing numbers would be invented. Address
position is the opposite case: held still, most reliable for the pose model,
and where the cheapest improvements live.

### 14.6 Fitting — `src/lib/fitting/engine.ts`, `/fitting`

Shaft flex, driver loft, club length, iron category and ball, each carrying
`confidence: measured | estimated` and the inputs it came from. Clubhead
speed is the median of up to five recent measured swings — not the latest
(rides on one clip) and not the max (systematically over-fits, putting a
golfer in a shaft too stiff for their Tuesday swing).

It degrades by design: length and iron category need no speed at all, so a
30fps down-the-line golfer still gets real recommendations plus a specific
list of what to change to unlock the rest.

### 14.7 Coaching language

Coaching is generated **in the golfer's language at generation time**, not
translated afterwards — swing instruction is idiomatic and machine-translated
English reads like a manual. `users.locale` drives it; UI chrome remains
English, and the picker is labelled "Coaching language" so it does not
promise otherwise.

`validateGrounding` gates club-delivery vocabulary on the metric being
present: the coach may say "clubhead speed" only on a swing where clubhead
speed was measured.

## 10. Explicitly out of scope

Do not build these. Do not stub them "for later" in a way that adds dependencies.

- **Model training or fine-tuning.** Use pretrained weights only. Expose `SWINGNET_CHECKPOINT_URL` as an env var so a checkpoint trained elsewhere can be dropped in without a code change.
- In-browser video *recording* of swings (§2.4). Note the Live Coach (§14.5) reads a live camera without recording or uploading anything — that is a different thing and is in scope.
- SMPL meshes and avatar reconstruction.
- Native mobile apps.
- A coach-facing multi-student dashboard.
- Real payment processing beyond Stripe test mode.

### Scope changes — 3D pose and club tracking

Two items moved **out of this list and into the product** (§14), by explicit
product decision:

- **3D pose playback** (was: "3D pose, SMPL meshes, or avatar reconstruction")
- **Club and clubhead tracking** (was: "Club or clubhead tracking")

⚠️ **The original exclusion of 3D pose carried a patent rationale, preserved
here verbatim so the decision is not lost:**

> *3D pose, SMPL meshes, or avatar reconstruction. Sportsbox holds granted US
> patents in this area (see US 11,640,725) — a 2D metrics product sits well
> outside those claims and that is deliberate.*

What is now built is skeletal 3D playback from MediaPipe's `pose_world_landmarks`
— joint positions in metres, rendered as a stick figure. No mesh, no avatar,
no SMPL. That is a narrower thing than what the original note excluded, but
it is not the 2D-only posture the note was written to protect. **This is a
question for counsel, not for this document.** Nobody on the engineering side
has assessed the claims of US 11,640,725 against what was built.

The club-tracking exclusion carried no stated rationale and reads as a scope
decision rather than a legal one.

## 13. How to work

- **Ask before deviating** from the stack or the contract in §3. Everything else, use your judgement.
- Commit at each checkpoint with a clear message. Do not produce one enormous commit.
- When you finish a phase, **stop and summarise** what you built, what you assumed, and what you need decided.
- Prefer boring, obvious code. This will be read by a team later and recalibrated by non-authors.
- If something in this spec is wrong or impossible, **say so rather than working around it silently.**
